# PX3 Synth 0.8.0: Architecture Assessment

Status: clean-generation assessment and tested scene-tree foundation; broader
0.8 architecture and performance gates remain in progress.

## Recommendation

Treat 0.8.0 as a clean architecture generation. Compatibility with 0.7.x state,
presets, parameter IDs, automation and layouts is explicitly not a constraint;
do not carry aliases, migrations, synchronization shims or old layout rules
solely for 0.7.x. Keep DSP algorithms and realtime techniques where they remain
good choices, but replace surrounding ownership/data models when a new model is
cleaner.

The normalized-region prototype has been replaced with a typed
`InstrumentSceneDocument` that owns layout, style tokens, stable UI IDs,
containment, ordering and parameter binding metadata. JUCE remains the
rendering/input/accessibility backend. The scene tree now drives the primary
Synth panel composition; individual control registration and internal panel
layout conversion remain unfinished.

## Current Architecture

- **Editor:** A JUCE retained-mode `Component` tree. `PluginEditorView.cpp`
  places six top-level surfaces (OSC, MOD, AMP, FLT, FX, MIX), with Settings
  accessed separately; the editor also owns the preset workflow, performance
  controls, keyboard, macro strip, and overlays. Panel internals are mostly
  hand-laid out. `UIConfig` supplies style values and rectangle lookups, but its
  Flexbox/JSON arrangement is not adequate as the 0.8 scene-graph source of
  truth. `PX3_DEBUG_PANEL` gates the existing console; a separate
  `PX3_UI_DESIGNER` gates the inspector and selection overlay. Its typed scene
  schema covers node kinds, child relationships and reusable style tokens;
  shared and internal control layouts still use UIConfig.
- **DSP:** The processor orchestrates source stems, mixer buses, modulation and
  FX. Voices own oscillator, filter and envelope runtime. Oscillators are
  band-limited; the immutable wavetable pyramid is shared, built off the audio
  thread and handed over through `WavetableSlot`. Filters are JUCE IIR stages
  plus a separate comb resonator, not classic ladder/Curtis/ARP topologies.
- **Modulation:** Three global LFOs, three per-voice modulation envelopes and
  five macro controls feed a shared destination registry/normalized-value
  accumulator. Each LFO/envelope has a current assignment and signed amount;
  macros already support multiple routes. LFOs have free rate, waveform,
  ramp-time and key-sync controls, but no distinct tempo/host-clock sync modes.
  The current registry and DSP path are fixed-size/atomic and avoid string
  lookup and allocation in the audio callback.
- **State:** Host state is now grouped `PX3_STATE` schema v1; parameter values
  live under catalog module groups, while order, routes, envelopes and other
  non-parameter data remain dedicated children. Presets wrap the same patch
  state in `PX3_PRESET`. Flat 0.7 parameter state is rejected, not migrated.
  Presets exclude the selected UI page; global editor preferences remain
  separate from patch state.
- **Effects:** Effect engines live in `shared/DSP`, consume block settings and
  process sample frames; standalone effect products use the same engines. Keep
  that boundary. LUCY is documented as lossy spectral degradation (not a
  bitcrusher); MOOD is a micro-looper with reverb/delay/slip modes; DOOM is a
  distinct two-channel micro-looper/spatial engine. These functions overlap at
  the broad “time/degradation” level but are not interchangeable engines.
- **Existing visual/DSP tools:** JUCE software painting is the default; the
  wavetable display already has an isolated OpenGL renderer. The test executable
  has GPU-render checks. Do not broaden GPU usage without profiling.

## Retain / Replace

| Area | Decision | Reason |
|---|---|---|
| Processor bus boundaries, preallocation and wavetable handoff | Retain where measurements confirm value | These are realtime engineering strengths, not 0.7.x compatibility baggage. Re-profile after new interfaces land. |
| Flat legacy parameter declarations and IDs | Replace | Define one declarative parameter catalog grouped by instrument module, with new 0.8 IDs and host-facing metadata. No 0.7 aliases. |
| State version 13 migration branches and legacy shape | Replace | Grouped `PX3_STATE` schema v1 now validates the complete parameter set before applying it. No 0.7 migration path. |
| Shared FX DSP engines | Retain engines; refactor registry/settings | Keep all effects available in the Synth and standalone products, but use typed effect descriptors and per-instance state rather than freezing old parameter layouts. |
| Wavetable analysis, mip pyramid and thread handoff | Retain | These provide band-limiting and realtime-safe ownership. Revisit import/UI/resource packaging independently. |
| Fixed editor composition and panel-owned layout | Replace progressively | Use an instrument scene tree and layout engine; keep JUCE controls as rendering/input primitives behind stable node bindings. |
| Synth Flexbox/JSON layout | Replace as the Synth source of truth | A typed tree with row/column/grid/overlay constraints and reusable tokens better serves the designer than adding more ad hoc JSON keys. |
| UI designer | Keep developer-only | `PX3_UI_DESIGNER` excludes inspector, selection, handles, authoring and history from release builds. |
| One-assignment-per-LFO/envelope representation | Replace | Compile fixed-capacity route slots into a bounded immutable evaluation plan. No legacy assignment adapter. |
| Filter/FX algorithms | Retain useful algorithms; replace model plumbing | Implement new distinct models and parameter organization in the clean schema; no need to append around old indices. |

## Research Findings and UX Direction

- Hardware front panels make signal order and control ownership legible through
  grouping, direct labels and dedicated high-frequency controls. Roland describes
  the JUNO-X as direct controls with an LCD for deeper parameters; Sequential
  positions the Prophet-6 around intuitive controls without menu diving. Apply
  the interaction principle, not their panel artwork: a compact OSC-to-filter-to-
  amp primary surface, with advanced detail in focused secondary views.
- Serum's overview separates oscillators, filters and effects and provides a
  dedicated modulation matrix. The useful pattern is a visible primary synthesis
  surface plus a specialized routing view, not copying its layout. Keep FX and
  MIX distinct as requested. Prototype a MOD/PATCH surface reachable by a
  dedicated tab/shortcut; do not make TAB alone the only discoverable route.
- VCV Rack documents direct port-to-port cable creation, moving/deleting a cable
  by its plug, modifier-assisted fan-out, explicit signal labels/tooltips and
  readable panel density. For PX3, use these as interaction cues: clear source
  and destination rails, hit-sized endpoints, selected-cable highlighting,
  amount shown on selection, filtering/grouping for dense routes, and a visible
  keyboard-accessible list fallback. Do not place patch points permanently
  between common synth controls.
- JUCE components already expose hierarchy, bounds, IDs, listeners,
  accessibility and repaint-driven drawing. Use JUCE as the retained-mode
  execution backend, not as an implicit layout database. A typed scene tree
  owns nodes, constraints, ordering, styles and parameter bindings; the runtime
  adapter resolves it into registered JUCE controls. The designer edits the
  tree transactionally. Release builds consume the finalized scene/tokens but
  compile out the inspector, selection, handles, authoring and history code.
- Use JUCE painting for static panel materials, knobs and indicators first.
  Existing OpenGL is already thread-backed and requires explicit attach/detach
  lifecycle; an always-repainting context would add synchronization, GPU and
  host-compatibility cost. Consider a narrowly scoped cable renderer only if a
  CPU prototype with many active routes misses measured frame-time goals. Keep
  repaint event-driven and cache only static layers when measurements justify it.

## Architecture Proposals

### Owner-provided visual reference

The owner supplied an OVERON-2V front-panel image as the reference for the new
UI look. Use its visual grammar, not its branding, artwork, control names or
two-voice architecture:

- One continuous charcoal/near-black faceplate with subtle tonal depth, rather
  than colored floating cards or rounded panel boxes.
- Bright, thin vertical section dividers and horizontal subsection rules.
  Grouping follows signal ownership and shared control baselines.
- Compact, bold white technical labels, mostly uppercase, with an obvious
  hierarchy between section titles, control captions and port labels.
- Metallic rotary caps, dark collars, clear white pointers and readable scale
  arcs. Distinguish primary and secondary controls by size and placement.
- Sparse colored LEDs and selected/modulated indicators. Color conveys state
  or routing; it should not tint entire module backgrounds and borders.
- Physical-looking switches and patch sockets with clear input/output labeling.
  Use sockets for actual patchbay endpoints, not decorative or nonfunctional
  controls on the primary surface.
- Dense, aligned control groups with enough space to read captions and operate
  controls. Preserve PX3's adaptive layout and separate FX/MIX views rather
  than reproducing the reference's very wide fixed panel.

The current primary surface now uses one dark faceplate, square neutral card
outlines, neutral rotary progress arcs and a weighted OSC-to-filter-to-AMP row.
Graph traces and live enable indicators retain semantic color. Keep this
override Synth-scoped; standalone FX cards must keep their current identity.
The primary row has been inspected at the 1518 x 918 default, but compact-width
art review and repeatable UI paint-cost measurements remain outstanding.

### Primary UI and layout editor

Design a front-panel scene from the instrument's signal flow, not the old tab
ownership. The primary surface exposes oscillators, filter, amp envelope and
performance controls together when width allows, with an adaptive compact
layout/secondary views when it does not. FX and MIX remain distinct surfaces;
MOD/PATCH is a focused alternate view. Preset/global utility controls belong to
the same physical header, not a website nav bar.

Replace the region-only JSON prototype before broad conversion with an
`InstrumentSceneDocument`: versioned scene roots; stable UI-node IDs; parent and
child relationships; control/container/decoration types; intrinsic/min/max
dimensions; row/column/grid/overlay layout policies; ordering; theme tokens;
and a separate optional parameter binding ID. The layout engine resolves a
document into registered JUCE components on construction, resize or edit, not
per audio block or per animation frame. Reusable control styles cover knobs,
switches, LEDs, labels, meters, section rules and patch ports. The visual
designer edits supported data properties and tree relationships in one undoable
transaction; it does not expose arbitrary C++ behavior.

The implemented `InstrumentSceneDocument` replaces the region-only prototype
with schema-v1 nodes and style tokens. It resolves absolute, row, column, grid
and overlay layouts and validates edits transactionally. `UIConfig` remains
temporarily for shared FX surfaces and panel internals; the Synth scene and its
theme should migrate as one authority. No 0.7 layout conversion is needed.
`PX3_UI_DESIGNER` excludes the inspector window and selection handles from
shipping builds. Document edit/history methods currently remain in the shared
scene model; authoring-code isolation is not yet complete.

### Modulation and patchbay

Use a typed modulation graph with stable source, destination and route IDs;
depth, polarity, curve, slew and scope are route properties. Sources include
LFO, envelope, key tracking, note/MIDI, random/slop, macro and host/audio clock.
LFO phase policy distinguishes free-running, tempo division, transport/MIDI
clock and note/key retrigger. Envelopes may target synthesis parameters, LFO
controls or other envelopes where scope is well-defined.

Route edits validate endpoints and reject cycles on the message thread, then
compile to a bounded immutable evaluation plan. The audio thread traverses only
preallocated data in topological order; it performs no allocation, locking,
string lookup or dynamic graph walk. Source scope (global/per-voice) and
destination update rate (sample/block/control) are explicit, so envelope-to-LFO
and per-voice slop do not get hidden behind processor special cases. Choose a
fixed route-slot capacity at plugin construction; slot depth can be a stable
host parameter while source/destination assignment remains patch data.

### Parameters, synthesis and FX

Define one `ParameterCatalog` as the source for host parameter creation, UI
binding, units/ranges/defaults, display formatting, grouping, modulation
capability and automation metadata. Use hierarchical 0.8 IDs such as
`voice.osc1.tuning.octave`, `voice.filter1.cutoff`, `mod.routes.slot01.depth`
and `fx.chorus.mode`. The host may expose a flat parameter list, but its
categories and IDs follow the instrument's module structure. Delete duplicate
legacy controls and one-off ID migrations rather than synchronizing old and new
parameters.

- **Oscillators:** use explicit octave, semitone and cents concepts. Keep
  `.px3wt` frame spectra and the anti-aliased immutable mip pyramid unless a
  quality test demonstrates a better format. Package referenced tables in the
  0.8 preset resource container by content hash. Diagnose supersaw/polyphony
  cost with fixed voices, modes and rates before changing its kernel. Rework
  each mode's macro labels/ranges around its intended timbre; new 0.8 parameter
  IDs may use the clearer names directly.
- **Filters:** model ladder, Curtis and ARP as distinct topologies/characters,
  with a shared filter interface and explicit key-track source. Resonance and
  self-oscillation must be stable under parameter sweeps. Choose oversampling
  only from alias/CPU measurements.
- **Modulation targets:** expose route depth as host automation slots with
  fixed capacity; store route source/destination/curve/scope in patch state.
  UI nodes bind by parameter ID, never array index or hidden knob order.
- **FX rack:** retain every requested effect. Represent each as a descriptor
  (stable 0.8 ID, typed settings schema, bypass/mix, processor factory and UI
  component). Store instances and order in a typed rack tree. Preserve reusable
  shared DSP kernels where they remain useful; refactor control models freely.
  Lucy remains spectral degradation, Mood remains a micro-loop effect, and Doom
  remains distinct. Make surface names literal and mode-specific. Mood Slip can
  be designed as tape-head/reverse behavior in 0.8 without preserving its old
  semitone interpretation. The future consolidation review must not remove FX
  during 0.8.0.

### Presets and state

Start with `PX3_STATE` schema version 1 for the new generation, grouped into
`GLOBAL`, `VOICE`, `OSCILLATORS`, `FILTERS`, `ENVELOPES`, `MODULATION_GRAPH`,
`FX_RACK`, `MIXER`, and `UI_PREFERENCES`. There is no 0.7.x reader or migration.
Within 0.8.x, state application validates the full tree before mutating the live
processor; bad or unknown major schemas are rejected atomically. Parameter
values have one authority, and route/effect/oscillator-specific state is nested
under its owning module rather than encoded in unrelated flat properties.

Make `.px3preset` a deterministic ZIP package containing a JSON manifest, the
structured patch document and only referenced external resources. Custom
wavetable resources use the existing `.px3wt` spectral-frame payload and a
content hash; the derived mip pyramid is rebuilt off-thread. This makes presets
portable without copying the same table pyramid into every preset. Future
0.8.x schema versions get explicit migrations; that is forward evolution, not
a 0.7 compatibility shim.

## 0.7.6 Baseline

Measured on the current clean checkout, commit `24986e4`, version `0.7.6`, arm64,
48 kHz / 512 samples (10.667 ms budget), using the existing
`build/diag` RelWithDebInfo tools. The benchmark runs the shipping DSP path
(`PX3_DIAGNOSTICS=0`), 400 measured blocks x 5 sweeps. Compare future builds
with the same toolchain, machine, configuration and scenarios. These are local
reference values, not cross-machine promises.

| Scenario | Median us | p99 us | Max us |
|---|---:|---:|---:|
| Idle, no voices | 91.0 | 132.9 | 210.0 |
| 1 voice | 124.5 | 174.1 | 451.4 |
| 16 voices, typical | 570.0 | 694.1 | 984.5 |
| 64 voices, max | 1,558.5 | 2,221.3 | 7,225.5 |
| 16 voices, all four sources | 920.7 | 1,046.2 | 1,208.2 |
| 16 voices, everything on | 3,482.8 | 3,772.5 | 10,434.6 |
| 64 voices, everything on | 8,734.1 | 9,425.8 | 23,792.8 |
| 16 voices, supersaw | 3,128.7 | 4,163.5 | 50,085.0 |
| 64 voices, wavetable | 5,467.2 | 6,522.0 | 216,293.5 |

The large max values are scheduler/outlier-sensitive; use repeated median and
p99 comparisons, with documented tolerances, rather than treating a single max
as a deterministic DSP regression. Still investigate repeatable deadline
misses and report max separately. Historical v0.7.6 release notes report
603 us for 16 voices and 9,064 us for 64 voices with all effects, measured in a
different pass/configuration; use the fresh rows above as the 0.8 comparison
baseline instead.

Additional baseline checks:

- Correctness suite: **1,537 passed, 0 failed**.
- `PX3Diag rtsafety`: **0 allocations** in `processBlock` across tested MIDI,
  filters, release tails, 48 voices and full FX/analog stress configurations.
- Memory benchmark: 12.6 MB process RSS before a processor; +26.2 MB first
  instance; +22.9 MB average incremental instance through eight. Heap use
  returned to baseline after destruction; allocator-retained footprint was
  +41.2 MB. Record heap and footprint separately.
- **UI baseline partially captured:** rebuilt and verified the 0.7.6 standalone
  from this checkout. Captured the OSC surface on a 5120 x 2880 display with a
  1322 x 826 logical editor window. A 3-second `sample` trace includes repeated
  message-thread component painting (including `PianoKeyboard::paintKeyboard`)
  and CoreAudio `processBlock` activity. One process-only `top` sample varied
  widely and includes audio callbacks, so it is not a UI CPU metric. No
  reproducible frame-time percentiles, UI-only idle/active CPU, automation
  latency, resize timing, construction timing or preset-load timing are
  available yet. The historical release audit's 170 ms construction and
  10.32 ms full repaint remain non-comparable. Capture those with a repeatable
  host/display harness before claiming no UI regression.
- **Launch note:** LaunchServices starts the standalone with `/` as its working
  directory in this environment; the 0.7.6 UIConfig read blocked during startup
  in that path. Direct launch from the repository with explicit
  `PX3_UI_CONFIG_PATH` loaded successfully. Keep the harness launch method fixed
  and document it for later comparisons.

The strict `0.8.0 >= 0.7.6` performance claim is not yet established for the UI,
multiple sample-rate/block-size combinations, initialization, preset latency or
UI automation. Those are explicit gates, not assumed passes.

## Scene Foundation Verification

- Designer-on standalone compiled and linked after the inspector grew to twelve
  property rows, including editable min/max dimensions. Scene min/max edits are
  validated and transactional; a zero maximum means unbounded.
- Rebuilt designer-off tests: **41 scene tests** and **25 editor-layout tests**,
  all passing; the full suite reports **1,589 passed, 0 failed**. Scene visibility now propagates
  through ancestors across every layout mode, persists through serialization,
  and is undoable through the designer's Visible checkbox.
- Release shared-code build with `PX3_UI_DESIGNER=OFF` and
  `PX3_DEBUG_PANEL=OFF` succeeds. Its compile database excludes
  `UILayoutDesigner.cpp`; its archive contains no `UILayoutDesignerWindow`
  symbols after the shared card renderer gained its optional hardware mode.
  This is not a plugin-format packaging or host validation pass.
- The primary composition is a weighted OSC/FILTER/AMP row; regression coverage
  checks order, full-height allocation, no overlap and a minimum AMP width.
  At the 1518 x 918 default, the panel uses a single dark faceplate, square
  neutral card outlines, neutral rotary arcs and compact OSC/ADSR captions.
  Dedicated secondary views remain available with stable logical tab IDs.
- The current-schema designer save/restart interaction still needs a native
  runtime smoke test. Parameter-control kind, label and catalog-backed binding,
  editable min/max constraints and visibility are now inspector-editable;
  style-token creation/edit remains follow-up work.
  Full release authoring-code isolation is verified at shared-code level, but
  not yet at plugin-format packaging or host level. No UI performance parity
  claim is made.

## Parameter Catalog Foundation

- `ParameterCatalog` now indexes all **327** Synth parameters, captures their
  current range/default/unit/automation metadata and registers them in nested
  JUCE host groups (VOICE, MODULATION, MIXER, EFFECTS, PERFORMANCE and GLOBAL).
  `getParameters()` remains the flattened host interface; state/preset round
  trips and the complete **1,589-test** suite pass with the grouped tree.
- The grouped state foundation is now wired into sessions, presets, INIT and
  regenerated factory presets; old state versions are rejected without
  mutation. The preset reader requires wrapper schema v1, state schema v1,
  complete catalog values, and an assets manifest rather than filling missing
  parameters from current defaults. Factory library v7 regenerates grouped
  states; INIT is built from catalog defaults. Oscillator and sub-oscillator
  controls now use hierarchical `voice.oscN.*` and `voice.sub.*` IDs, including
  tuning, source mode, macros, wavetable controls, harmonics, and pitch-mod
  destinations; factory definitions, modulation bindings and tests use them.
  Other parameter IDs and constructor declarations remain 0.7-derived, and
  catalog metadata is still inferred from JUCE parameter objects rather than
  serving as the typed creation source. No 0.7 aliases or migration are
  intended.

## Revised Implementation Order

1. Finish the missing performance baseline: deterministic UI frame/CPU/latency
  harness, preset/init timings, and the DSP sample-rate/block-size matrix.
2. Define the 0.8 parameter catalog, grouped state tree, preset package/resource
  model, modulation graph types and scene-document schema before broad rewrites.
3. Replace the Synth Flexbox/rectangle authority with the typed scene/layout
  engine and shared design tokens. Extend the visual designer to edit real
  hierarchy, constraints, styles and registered controls.
4. Recompose the primary hardware-style surface and MOD/PATCH navigation. FX
  and MIX remain distinct surfaces; common voice controls are shallow-access.
5. Convert modulation to the graph plan, then implement oscillator/filter
  changes and FX refinements as measured, testable slices.
6. Integrate and run regression, realtime-safety, preset round-trip, UI, DSP
  and memory comparisons. Repeat measurements after the final art pass.

The 0.8.0 state/preset schemas and parameter IDs start fresh; no 0.7.x
compatibility shims or migrations are planned. Any new 0.8.x schema change still
needs a deterministic versioned migration. The user-table payload stays
`.px3wt` because its spectral-frame representation is already validated and
sample-rate-independent; the new preset container will own/reference those
resources by content hash.
